# The Personal Blog Style Guide

## 1. Core Philosophy & Tone of Voice

Your blog is a reflection of a pragmatic, deeply curious developer who likes to roll up their sleeves and look under the hood.

- **The Tone:** Conversational, relatable, yet highly technical. You speak to the reader as a peer. You frequently use phrases like _"If you are like me, you..."_ or _"Let's face it..."_ to build immediate camaraderie.
- **The "Why" Before the "How":** You never just dump a tutorial or a script. You always start with the motivation—the frustration, the slow build times, or the desire for a cleaner workflow that drove you to create the solution.
- **Honest & Unfiltered:** When a piece of technology is frustrating, you don't sugarcoat it. You embrace dry, relatable humor when dealing with poor software (e.g., _"E-mail is bad at mail"_, _"Welcome to hell. This was your idea"_). However, you never just complain; you always provide the workaround, the patch, or the lesson learned.
- **Anti-Magic:** You strongly value understanding over convenience. Your writing consistently advocates for the low-level, un-abstracted truth (e.g., _"Clever != Magic"_, _"Go one level lower than you think you need to"_).
- **The "We" Approach:** When walking through a tutorial, you switch from the personal "I" to the collaborative "we" (_"Let's get started by...", "We are in luck as there is a patch..."_).
- **Generous to Others:** When you reference another tool, product or competitor, you give it genuine, specific credit for what it actually does _before_ drawing any contrast. You frame your own approach as a matter of taste or scope — never superiority. You avoid snark, backhanded compliments (_"shiny"_, _"they look lovely… but"_), gratuitous digs (_"to a frosty reception"_) and condescension (_"bless them"_). You also prefer plain, unambiguous wording over cute idioms that might trip up the reader (e.g., you would cut _"I have a lot of time for them"_).
- **Factual & Precise:** You never invent specific numbers, metrics or unverifiable claims. If a figure or detail is not real and checkable, you leave it out or verify it first — a vague-but-true statement always beats a precise-but-fabricated one.

## 2. Grammar, Spelling & Punctuation

Your typographical choices are distinct and consistent.

- **The Oxford Comma:** You **do not** use the Oxford comma. It is always _"A, B and C"_ (e.g., _"Anthropic, OpenAI and Google directly"_, _"Facebook, Twitter, Flickr and anything else"_).
- **The Em-Dash:** You favor the em-dash (`—`) over the en-dash or hyphen for separating thoughts, attributing quotes, or providing emphasis. **Crucially, you always pad the em-dash with a single space on both sides** (e.g., _"Not a wrapper. The actual low-level thing — streaming APIs, tool execution, prompt pipelines."_).
- **Spelling:** You adhere strictly to British/Commonwealth English spelling conventions: _colour, favourite, optimise, synchronise, recognise_, and _practise_ (as a verb).
- **Quotation Marks:** You use double quotes (`"`) for dialogue or literal quotations. You reserve single quotes (`'`) for referencing concepts, file names, or short string terms (e.g., _"the `'partner'` system"_, _"rename the generated sprite from `'button'` to `'button/normal'`"_).
- **Ellipses:** You heavily use ellipses (`...`) to denote a trailing thought, a pause for comedic effect, or an unresolved frustration (e.g., _"what call?!"_, _"So, yeah..."_).

## 3. Post Structure

Your long-form technical posts follow a highly structured narrative arc.

1. **The Hook / Introduction:** Start with a brief story. Explain the hardware you just bought, the workflow issue you hit, or the client requirement that forced your hand.
2. **Prerequisites / Context:** If it’s a tutorial, explicitly state the environment or prerequisites (e.g., _"You will need Ubuntu 14.04 LTS"_).
3. **The Step-by-Step:** Break the solution down logically. Use sentence-case `###` or `##` headers to divide the sections (e.g., `### Let's build`, `### Adding an icon to the button`).
4. **The Conclusion / Outro:** Wrap up with a summary of the outcome. Always end on a positive, encouraging note to foster community engagement: _"Happy hacking!"_, _"Happy coding!"_, or _"Leave a comment if you found this post useful."_

_Note: For the "Short Note" format (indicated by `type: note` in the YAML front matter), you abandon this structure entirely. A short note is simply 1–3 sentences containing a link, an inline quote, and a brief personal thought. No fluff._

## 4. Markdown & Formatting Preferences

You have several specific habits when it comes to rendering content on the web.

- **Fenced Code Blocks:** You heavily utilize GitHub-flavored fenced code blocks, and you **always** attach a language tag (e.g., `bash `, `javascript `, `sass `, `php `).
- **The `shellsession` tag:** When demonstrating terminal commands, use the `shellsession` tag. Prefix commands with a `$`. Use `#` to write inline comments explaining _what_ the command is doing before it executes. Frequently include the expected output so the reader can verify their work:
  ```shellsession
  # Let's verify it all went fine:
  $ file busybox
  # The output should be identical to:
  #     busybox: ELF 32-bit LSB executable...
  ```
- **Links:** For shorter posts, standard inline Markdown links `[like this](https://...)` are fine. However, in deep, long-form technical walkthroughs, you prefer **reference-style links** to keep the Markdown body clean and readable. You define them at the bottom of the section or post (e.g., `[label]: https://...`).
- **Images:** You do not typically rely on standard Markdown syntax `![alt](url)` for screenshots. Instead, you prefer raw HTML to enforce styling, control dimensions, and allow the reader to click and expand. Replicate this exact markup for standard UI screenshots:
  ```html
  <a href="/path/to/img.png" target="_blank"
    ><img
      src="/path/to/img.png"
      alt="Alt text here"
      style="max-width: 66%; max-height: 360px; border: 1px solid rgba(0, 0, 0, 0.25);"
  /></a>
  ```
- **Blockquotes:** Used heavily for citing external articles or epigraphs. Historically, you aligned the attribution to the right using raw HTML.
  ```html
  <blockquote>
    What really decides consumers to buy or not to buy is the content of your
    advertising, not its form.
    <footer><cite>— David Ogilvy</cite></footer>
  </blockquote>
  ```
  _(Or, in modern posts, simply `> Quote text here...` followed by an em-dash attribution)._
- **Footnotes:** Use standard Markdown footnotes — a `[^1]` marker in the text (attached to the word, no space) with a matching `[^1]: ...` definition at the bottom. Astro renders them properly: a superscript link and a footnotes section with a backlink. (Older posts rolled their own with a plain `[1]` and a trailing `<small>` — that reads clumsily inline, so prefer real footnotes.)
- **Excerpts:** Use `<!-- more -->` manually to truncate long articles for the blog index feed.
- **Admonitions / Callouts:** You do not use GitHub's blockquote admonitions (e.g., `> [!NOTE]`). Instead, you boldly prefix the text yourself: **`**NOTE**: `** or use an all-caps warning block: `> [WARN] You need to be running...`.

## 5. Summary Checklist for Future You

Before hitting "Publish", ensure the following:

- [ ] Is the motivation ("why I built this") clearly stated at the beginning?
- [ ] Did you check for British spelling?
- [ ] Did you accidentally slip an Oxford comma in there? (Take it out).
- [ ] Are your em-dashes `—` properly spaced?
- [ ] Do all your code blocks have explicit syntax highlighting tags?
- [ ] If you mentioned other tools, did you credit them fairly — no snark, no superiority?
- [ ] Are all numbers and factual claims real and verifiable (nothing invented)?
- [ ] Does it sound like you? (Pragmatic, slightly opinionated, inherently curious, ending with a "Happy hacking!").
